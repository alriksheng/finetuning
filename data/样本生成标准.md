# 样本生成标准

本文件是样本生成的唯一标准，后续新增项目、修改样本都按本文件执行。**动笔前必读：第七节“事实表述的准确性”、第十三节“定性指标与时效指标的处理”，以及 `data/rules/指标到成本计算规则.md`**，这两部分是专家多轮修改总结出的要求，最容易遗漏。旧的分层改写方法已全部删除，存档在项目目录之外：`~/Documents/Finetuning_旧方法存档_20261015/`。存档只作追溯，不作参考，不从中复制文字或做法。

## 〇、总体路径

### 1. 两类样本

| | 普通样本 | 专项样本 |
| --- | --- | --- |
| 教模型什么 | 按专家口径，对一个小节写出评审意见 | 把专家很少写、但要求掌握的规则学会 |
| 输入 | 小节或比对包 + 事实卡 + 条文 + 审核重点（按章节类型自动带） | 绩效指标表 + 成本构成表 + 审核重点（只带本规则一项） |
| 输出 | 推理 + 结构化意见（findings） | 推理 + 逐个指标的判断；每个项目一条汇总 |
| 意见来源 | 专家原话为主，模型撰写只限四种情形 | 模型带规则卡生成，经核验和专家确认 |
| 规格与核验 | `data/specs/<P>.py`，`build.py` | `rules/<规则>/<P>.py`，`build_rule_samples.py` |
| 现状（2026-10-15；新项目的专项量按第十节第 7 小节控制） | 5 个项目，61 条（含 5 条 L3-07 衔接意见） | 只做 L3-07 一条规则，5 个项目共 73 条，已进入训练（取 43 条） |

### 2. 每个项目同步生成两类样本

```
匹配 → 转换 → 切分小节 → 拆分专家意见
  ├─ 普通样本：定位证据、选事实卡、写推理 → build.py 核验
  └─ 专项样本：取指标表和成本表、逐项判断、汇总、改写成对 → build_rule_samples.py 核验
→ 专家确认表（普通样本 + 规则待定口径 + 逐项判断）
```

### 3. 微调：两类样本一起训练

两类样本列在同一个训练配置里，一次训练完成。有三个前提：

1. **准入**：规则卡经专家确认后，专项样本才进训练（`in_train`）。到训练时仍未确认的，只用普通样本训练；上线需要这项检查时，在输入中带规则卡全文作为保底。
2. **比例**：普通样本 : 专项样本 = 2 : 1（行数，普通样本含精标加权；`rule_ratio: 0.5`，用户 2026-10-23）。专项样本按分类平均挑选：汇总、合成、驱动成本、不适用、无对应成本项、需人工核对共 6 类，每类配额相等；某类不足时全取，缺额平分给其余各类；类内各项目轮流取，项目顺序按固定种子（`rule_seed`）打乱。每个项目的“不适用”类最多保留 2 条。
3. **衔接**：规则进训练时，把它加进普通样本相应章节的审核重点，并用专项汇总补普通样本的意见；专家已提过的不重复补。见第十节第 6a 小节。

另外两项照常执行：带推理和不带推理两个版本都生成；精标样本权重为 2。

### 4. 验证

- **划分**：按“单位 + 项目类型”成组划分开发集和测试集。同一项目的两类样本在同一边，不会泄漏。
- **普通样本**：统计意见覆盖率、误报率、有依据率、条文遵从率。
- **专项样本**：做内化验证三组，即带规则卡、只带标签、都不带；另外单独统计效益、满意度类指标被误判为“不挂钩”的比例。

### 5. 上线时的用法

1. 切分报告，抽取事实卡。
2. 逐小节审核：输入自动带审核重点，模型写出意见。已经学会的规则，会在相应小节中直接写出意见。
3. 需要专门检查某条规则时：程序抽出指标表和成本表，只带规则标签，模型逐项判断并汇总，结果作为该小节意见的依据。
4. 列漏项清单，组装成正式评审意见。

### 6. 阶段

| 阶段 | 内容 |
| --- | --- |
| 1 | 5 个试跑项目的两类样本和专家确认表（已完成） |
| 2 | 专家确认：普通样本、L3-07 待定口径、逐项判断（第六轮，已完成）；L3-07 衔接意见等 5 条（第七轮，已采纳）；按 15 号、8 号文统一指标口径（2026-10-16，已完成） |
| 3 | 按确认的口径修改专项判断；L3-07 加进审核重点，补普通样本意见；打开 in_train（已完成，补充的 5 条意见待第七轮确认） |
| 4 | 实测 2 个项目的标注用量，再批量标注 112 个项目，两类样本同步生成 |
| 5 | 约 200 个项目到齐后划分开发集和测试集，跑基线（原版模型、老师模型） |
| 6 | 两类样本一起微调；在开发集上调比例、选检查点；在测试集上做三组对比和规则内化验证 |
| 7 | 第二条及以后的预制规则，按 L3-07 的流程逐条加入 |

## 一、基本原则

1. **意见用专家原话。** 每个要点的 `problem` / `suggestion` 直接取自评审意见原文 `raw/reviews/<项目>.txt`，只按要点拆分，不改写、不润色、不精简。
2. **只做登记过的最小改动。** 允许的改动只有以下四类，每处都写入 `edits`，写明原因：
   - 拆分带出的序号或部分标题，例如去掉“一是”“基本情况部分，”；
   - 经核对确认的笔误，例如 4.67 改为 4.76；
   - 输入中无法核验的取整数字，改为输入中的精确值，例如“800万”改为 811.75 万；
   - 拆分后句子不完整，需要补一个连接成分。用 `$END` 追加，并写明原因。
3. **模型撰写只限三种情形。** 每个模型撰写的要点都写 `reason` 和 `expert_text_ref`（对应的专家原话，没有就不写）。
   - ~~提示核实~~：2026-10-23 起不再生成（用户决定，原因：A 里出现 Q 里没有的事实，推理也无从由 Q 得出）。依据不在输入中的专家意见分三类处理，见第四节；已有的 74 条提示核实的处置记录在 `data/out/unlinked_hint_points.json`；
   - 模型补充发现：专家未提，比对数据发现的问题。专家已全部采纳（第八轮，用户 2026-10-19），此后同类要点不再送专家确认，reason 写“模型补充发现：<比对内容>；专家已采纳（第八轮）”。既有写法是表内或表文之间的金额、单价×数量、比例、降本口径比对，沿用该写法，不专门去查报告的数据错误；
   - 证据不足；
   - 条文改写合成：条文改了，答案必须跟着变。
4. **依据只能来自输入。** 推理过程和意见用到的每条事实，都必须在本条样本的输入中，即小节或比对包、事实卡、条文。规则的判断步骤可以写在推理中，并标注“依据：评审经验”。
5. **条文编号只出现在 think 中。** 意见正文不写条文编号，编号放在 `clause_ids`，由 `render_opinion.py` 单列依据。
6. **推理过程不简化。** 平均约 570 字，现为 561 字，范围 250–950。按第六节的步骤写。
7. **指标类内容按第十三节处理。** 凡涉及定性指标、时效指标、指标与成本的关联，无论写在推理、意见还是专项样本中，都按第十三节的口径、机制和量化方法执行，并过一遍该节的自查清单。
8. **一切以核验脚本为准。** 每次改动规格后都要重跑构建，`rejected` 必须为 0。核验通过不等于内容正确，但核验不通过的样本一律不用。

## 二、流程

| 步骤 | 做法 | 工具 |
| --- | --- | --- |
| 1. 匹配 | 报告与评审意见配对，少数在 `match/overrides.yaml` 中人工判定 | `scripts/match_reports.py` |
| 2. 转换 | docx 转 md（保留表格）；.doc 先经 LibreOffice 转换；PDF 用 pdftotext，扫描件需 OCR | `docx_to_md.py`、`convert_reports.py`、`pdf_reflow.py` |
| 3. 报告切分 | 识别目录、摘要、正文、附件，切成小节并标注 kind | `section_report.py <报告.md> data/specs/sections/<P>.json` |
| 4. 意见拆分 | 按部分和“一是／1.”拆成要点，保留原文 | `split_review.py <意见.xlsx> data/specs/review_points/<P>.json` |
| 5. 标注 | 为每个要点确定小节、证据摘录、事实卡字段、标签和规则；合并同一小节的要点；撰写推理；涉及指标的按第十三节处理 | Claude Code，写入 `data/specs/<P>.py` |
| 5a. 专项样本 | **每个新项目做完普通样本后，同步为当前的每条预制规则生成专项样本**（现为 L3-07 一条），见第十节第 7 小节；逐项判断按第十三节的口径和自查清单 | Claude Code，写入 `rules/<规则>/<P>.py` |
| 6. 构建与核验 | 见第五节；专项样本另用 `build_rule_samples.py` 核验 | `python3 -I scripts/build.py data`、`python3 -I scripts/build_rule_samples.py data L3-07` |
| 7. 专家确认 | 生成确认表，交专家判断；带上当前预制规则，表中会包含规则的待定口径和逐项判断 | `python3 -I scripts/make_review_xlsx.py data <轮次名> L3-07`；只出待确认的要点时加 `--pending`（不含已确认内容和规则表）。已确认样本中新增或修改的模型撰写要点，在该要点的 `reason` 末尾加“；待专家确认”，`--pending` 只出这些要点；专家采纳后删去该标记 |
| 8. 训练文件 | 按 `splits.yaml` 生成 | `python3 -I scripts/make_splits.py data` |

**批量生成**（剩余项目）：
- `scripts/prepare_batch.py` 自动完成第 1–4 步，分配编号，并在 `data/batch/manifest.csv` 中逐项列出需人工处理的情况；
- 标注时，每个项目单独调用一次非交互的 Claude Code（`scripts/run_batch.sh <编号…>`），执行 `data/batch/标注指令.md`；
- 结果说明写在 `data/batch/notes/<P>.md`，用时和费用记录在 `data/batch/logs/<P>.json`。

项目信息（名称、主管部门、金额、报告版本、评审时点、分组、项目类型、标注方式）写在 `data/specs/projects.json`。其中 `ptype` 取经常性、新建工程或政策，决定使用哪一套条文对应表和审核重点对应表。

完整重建：

```bash
python3 -I scripts/build.py data && python3 -I scripts/build_rule_samples.py data L3-07 && python3 -I scripts/make_splits.py data && python3 -I scripts/test_checks.py
```

## 三、规格文件 `data/specs/<P>.py`

模块变量：

- `SOURCE`：项目编号。
- `SECTIONS`：小节表。新项目用 `spec_lib.load(pid, 项目类型)` 从 `sections/<P>.json` 生成，项目类型取 `经常性`、`新建工程` 或 `政策`。
  - P001 为 PDF，按页定位：`chunks=[(页, 起锚点, 止锚点)]`；
  - 其余按行定位：`lines=[(起, 止)]`。
- `PACKS`：比对包，`{id: {label, a, b}}`。label 须为对应表中的 `pack:` 键。
- `CLAUSE_MAP`：章节 kind 对应的条文，新项目由 `spec_lib` 从 `clause_map.yaml` 生成。
- `CARD`：事实卡字段 `{name, value, loc, sec|page, qa, qb}`。摘录由锚点 `qa`…`qb` 从原文切片；`value` 中两位以上的数字必须出现在摘录中。
- `SAMPLES`：样本列表，字段如下。

**样本字段**

| 字段 | 说明 |
| --- | --- |
| `id` | 新项目用 `V4_<P>_<小节>` |
| `type` | 单点、跨处比对、推理链、缺失、多问题、事实卡抽取、漏项清单、无问题、证据不足 |
| `unit` | 小节 id 或比对包 id |
| `target` | 声明的可达性：full、partial 或 hint，必须与计算结果一致 |
| `card` | 放入输入的事实卡字段名 |
| `rules`、`clauses` | 规则编号、条文编号。条文必须在本单元的对应表中 |
| `evidence` | 全部要点的证据摘录，逐字取自报告 |
| `task` | 固定为“对本小节提出评审意见。”或“对比两侧小节，提出评审意见。”；事实卡抽取、漏项清单除外 |
| `source_kind` | 取值见下方说明 |
| `status` | 精标项目写确认进度；自动标注项目写“自动标注，待专家抽查”；以“候选”开头的不进训练集 |
| `notes`、`author` | 备注；推理作者，现为 `claude-opus-5-5` |
| `merged` | 同一小节多个要点合并时为 True |
| `think` | 推理过程，见第六节 |
| `points` | 要点列表 |
| 可选字段 | `answer_raw`：事实卡抽取、漏项清单的答案；`clause_override`、`mapped_override`、`must_quote`、`base_sample`：合成样本用；`history.expert_round1`：专家历次判断 |

`source_kind` 的取值：expert、model_supplement、candidate_no_issue、synthetic_clause_rewrite、synthetic_clause_irrelevant。

**要点字段（points）**

- 共有字段：`id`、`type`、`part`（所属部分，按原意见中的位置）、`label`（问题分类，取意见模板的分类）、`rules`、`clauses`、`evidence`、`target`、`source_kind`。
- 可选 `clause_ids`：显式指定输出的条文。不指定时，取本要点 `clauses` 中出现在 think 里的条文。
- 专家原话：`text_source='专家原话'`、`expert_text`（逐字）、`edits=[[原文, 改为, 原因]]`、`note`。
- 模型撰写：`text_source='模型撰写'`、`reason`、`problem`、`suggestion`、`expert_text_ref`。

意见拆分规则：专家原话在第一处“，建议”后拆开，前半为 problem，后半为 suggestion；以“建议”开头的整句全部归入 suggestion。

## 四、输入构造与可达性

**输入的组成**，按顺序为：

1. 【项目信息】；
2. 【报告段落】：小节或比对包两侧，带页码或位置标签；
3. 【事实卡】：只放本样本 `card` 列出的字段；
4. 【条文】：按“章节／比对包 → 条文”对应表选取，每条样本 3–8 段；评审时点填写后，按时点过滤；
5. 【审核重点】：按“章节／比对包 → 审核重点”对应表选取，见第十节；
6. 【任务】。

**对应表** `data/specs/clause_map.yaml` 分三套：

- 经常性：来自 P001、P002；
- 新建工程：增加 8 号文第十一条，即新增重大项目的方案比选；
- 政策：10 号文第四条（一）至（六），以及报告参考提纲。

摘要小节 `abs_xxx` 沿用对应正文小节的条文。

**可达性**：每条证据在“小节／比对包 + 事实卡 + 条文”中逐字查找。

- 全部找到为 full，可以直接用专家原话；
- 部分找到为 partial；
- 全部找不到为 hint。

依据不在输入中时，有两种处理：

1. **优先补事实卡**：把其他小节中的关键事实作为事实卡字段引入，使依据可达；
2. 补不了时**不再写提示核实**，按原因分三类（2026-10-23）：
   - **A 报告缺少该内容**（如专家要求补充后续年度预算安排，而小节只有当年度安排）：缺什么从输入就能看出，生成正常样本。意见用专家原话，证据取小节里本应出现该内容的那段（如财政资金安排建议），推理写“小节给出了什么、没有给出什么”，不下“全文没有”的断言；同一句话被拆成 a、b 两个要点的，并回专家原话全文；
   - **B 依据不在报告中**（页码、附件正文、外部文件的具体数字、报告没有的早年数据、专家引用的外地数据）：不作样本，记入 `data/out/unlinked_expert_comments.json`；专家原话中的页码等数字不在输入中，也通不过数字核验；
   - **C 专家表述与报告不符**（专家引用的数字、名称、结论与现有报告对不上，疑针对修改前的版本）：不作样本，同样记入上述文件。

## 五、核验清单（`scripts/build.py`，函数在 `scripts/checks.py`）

1. 证据摘录逐字出现在报告原文中；可达性的计算结果与声明的 `target` 一致。
2. think 和意见中的「引文」逐字出现在输入中，用“…”连接的各段分别核对。
3. think 中的算式逐个复算。
4. 数字来源：
   - 模型撰写的意见中，两位以上的数字必须在输入中，或是 think 中已验证的计算结果；
   - 专家原话同样要求，但豁免年份、〔YYYY〕N号文号和 GB 标准编号，这三类属于引用。
5. 引用的条文编号必须在本条输入中；`clauses` 必须在对应表中。
6. `expert_text` 和 `expert_text_ref` 必须逐字出现在评审意见原文中；来源为 expert 的要点必须有专家原话。
7. 写作规范只查模型撰写的意见：
   - 每条不超过 260 字；
   - 整句引用不超过 2 处，每处不超过 12 字；
   - 与输入连续重合不超过 24 字；
   - 不含条文编号；
   - 禁用词：本小节、请到、看不到、没有、只、却、这些、我们，以及绝对化用语完全、毫无、根本、绝对、不了；
   - 量化要求：每条不超过 200 字，单个分句不超过 100 字，“仅”最多 1 次，括号最多 2 处；
   - 标点：problem 以“，”或“。”结尾，suggestion 以“。”结尾。

   所有要点的 `part` 都必须是原评审意见中的部分名，即以“部分”结尾，或为总体、总体意见、降本增效情况、“三个标准”建立情况。
8. 条文改写合成样本：think 中必须逐字引用改写后的内容（`must_quote`）。
9. 任务文字必须使用固定写法。
10. 单条样本不超过 8500 字符，包括系统提示、输入和输出。这是字符数的代理上限，加入审核重点后由 8000 放宽；训练的 cutoff_len 用 MiniCPM-V 4.5 分词器实测后设定。
11. 事实卡字段的数值必须出现在摘录中。
12. 规则编号必须在 `rules/rules.yaml` 中。
13. 审核重点：每条样本 1–13 项，每项规则都必须有 `tag`；要点用到的每条规则都必须在本样本的审核重点中。

核验函数的单元测试在 `scripts/test_checks.py`。新增检查时，同时补充正例和反例。

## 六、推理过程（think）

1. 按标注的步骤写，常用步骤为：定位、摘录、核对、计算、条文、规则、结论。多问题样本按要点分段，写成“要点一：……”。
2. 摘录用「」逐字引用输入。数字计算写出完整算式，构建时会复算。
3. 引用条文时写编号，并用「」摘录关键句。条文编号只在这里出现。
4. 规则的判断步骤和阈值可以来自规则库，标注“依据：评审经验”。
5. 结论要与输出的 verdict 和意见一致：think 推出的结论，就是专家原话表达的结论。
6. 复杂度保持在平均约 570 字。不为缩短而删去核对步骤。
7. think 不受写作规范约束，但不得引入输入之外的事实。
8. **不把专家当作意见来源。** 样本是“输入（项目内容）→ 评审意见 → 推理”，推理和意见都以评审人的口吻写，不出现“专家要求”“专家所提”“专家所指”“专家引用”等说法（脚本 `SRC_EXPERT` 拦截，用户 2026-10-22）。推理里写报告缺什么，例如“本小节只给出当年度的预算安排，没有后续年度的安排”；页码、外部文件编号等只有专家原话才有的内容，不写进意见。若一条提示核实只能写成“专家说的与报告对不上”（专家数字与报告不符、专家意见与现有报告不符），不生成样本，在项目说明文件里记一笔。
8. 涉及指标的判断（定性指标、时效指标、指标与成本的关联），按第十三节的口径、机制和量化方法写，并对照该节的自查清单。
9. **每条样本的推理不少于 450 字**（事实卡抽取、漏项清单除外），构建时拦截（`build.py` 的 `THINK_MIN`）。

## 七、模型撰写意见的写法

按 `data/style/公文风格指南.md` 撰写：

- 公文风，基本句式为“问题定性或关键依据，建议／需／应 + 动作，目的”；
- 问题与建议不重复；
- 不整句摘抄报告，不写条文编号；
- 不用口语；
- 每条不超过 200 字，单个分句不超过 100 字；
- “仅”每条最多 1 次，括号最多 2 处。


### 事实表述的准确性（专家修改记录总结，`data/feedback/专家修改记录_早期轮次（工作簿1）.xlsx`）

专家逐条改写过 4 条样本、5 条模型撰写的意见，备注里写明了修改原因。下面六条要求由此总结而来（第 6 条来自第七轮），适用于所有模型撰写的意见，包括补充发现、L3-07 衔接意见和合成样本。推理过程（think）中的判断也按此执行。

| 要求 | 错误写法（原样本） | 专家的改法与原因 |
| --- | --- | --- |
| 1. **区分不同工艺、不同时期的口径**：历史做法与拟采用做法不同时，写明二者的差异，要求分别测算；不把“做法不同”判为“口径不一致” | 旧线清除“范围与口径不一致” | “历史年度主要采用简单拉毛工艺，与后续拟采用的机械打磨、高压水清除等工艺存在差异……区分不同工艺的成本构成”；原因：未区分历史工艺与后续工艺的成本口径 |
| 2. **金额要归属到它实际对应的事项**：一个金额只对应报告中写明的那一项，不扩大到相邻事项 | “机械打磨和高压水清除成本约15,053,463元”（该金额只对应机械打磨涂黑漆，高压水清除为待评审） | 删去金额；原因：成本金额归属不准确 |
| 3. **准确转述报告的方法和内容**：报告只说某一部分怎么做的，不扩大为整体；报告已有相关内容的，不写“未涉及”，改写“对应关系不明确”“需进一步明确” | “成本定额仍按历史平均值修正”（报告原文是工程作业量依据历史平均值修正）；“没有旧线清除工序的基线”（报告设有“清除标线”指标） | “报告虽设置了‘清除标线’相关指标，但该指标与……工序的对应关系及相关工作量基线尚不明确”；原因：方法表述不准确、基线表述需调整 |
| 4. **不把近似说成绝对，判断留有余地**：99.95% 不写“完全一致”；不写“脱钩”“反映不了”这类定论，用“衔接不足”“尚未充分”“难以反映”“有待进一步明确” | “实际支出与合同价完全一致”“付费与实际工作量、质量脱钩” | “现行结算方式与实际巡查频次、里程的衔接不足”；原因：事实表述不准确、判断过于绝对 |
| 5. **两个口径不同的数字，要求说明差异，不直接要求统一**：先要求说明各自的成本构成、测算依据和适用范围，再分析差异原因、论证合理性 | “建议统一单价口径” | “明确不同单价的成本构成、测算依据及适用范围……分析单价差异原因，论证建议单价的合理性”；原因：不同单价的测算口径需区分，不宜直接要求一致 |
| 6. **不硬性建立关联**：指标与成本、问题与建议之间的因果关系要符合常识、说得清机制；说不清的不写 | “相关指标仅为及时率……建议补充标志板、杆件、标线等抢修工程量指标” | 删除；原因：抢修及时性与维修人员响应时间有关，与抢修工程量无关，不能强行建立关系（第七轮）。详见第十三节第 3 小节 |

另外两条写法上的要求：

- **少列举具体名称**：技术、工艺、设备等名称不逐一罗列，概括为一类，例如写“信息化管理和新技术应用”，不写“任务分派系统、数据采集终端、无人机巡检、高压水铣刨除线”。原因：专家认为技术名称列举过多。
- **专家改写的句式可作参照**：先用一句话定性并以句号结束，如“巡查检查单价差异较大，测算依据需进一步说明。”；再用“报告显示……”“报告虽……但……”交代事实；最后写“建议……，以／提高……”。定性多用“不够充分”“尚未充分”“需进一步明确”“衔接不足”。

**核验**：“完全”“毫无”“根本”“绝对”“不了”已加入模型撰写意见的禁用词，由脚本拦截。第 1、2、3、5 条脚本无法判断，撰写时自查：每个判断都要能在输入中找到对应原文；每个金额都要核对它在报告中对应哪一项。

## 八、输出格式与组装

- 输出为 JSON：`{task, findings:[{issue_type, rule_id, verdict, evidence:[{source, loc, quote}], clause_ids, basis_type, problem, suggestion, part}]}`。事实卡抽取、漏项逐项判断按各自的字段输出。
- 字段的取值规则：
  - verdict：type 为证据不足或无问题时取同名值；其余为问题。
  - basis_type：
    - 意见中不含“依据：评审经验”时，有条文为政策，无条文为评审经验；
    - 意见中含“依据：评审经验”时，有条文为政策+评审经验，无条文为评审经验。
- 系统提示由 `build.py` 中的 SYSTEM_BASE 加【任务类型】组成，任务类型为小节审核、比对包、事实卡抽取或漏项逐项判断。
- 正式意见由 `scripts/render_opinion.py` 组装：
  - **所属部分不写进意见正文**（专家第六轮意见）。不写“××部分，”“完善分析范围：”这类开头，部分名由 `render_tags` 单列为标签，作辅助展示（`meta.opinion_tags`，确认表“标签”列）；模型输出中的 `part` 字段不变；
  - 同一部分的多条意见写成“一是……。二是……。”；降本增效情况、“三个标准”按“1.……”编号；
  - 专家原话中自带的位置说明（如“实施内容部分，……”“针对需要补充的复划线清除部分，……”）属于原话内容，保留不改。
- 每条样本生成两个版本：带推理（think）和不带推理（nothink）。不带推理的版本以 `<think>\n\n</think>\n\n` 开头。

## 九、合并与合成

- **合并**：同一小节（或同一比对包）的多个要点合并为一条多问题样本（`merged=True`），think 按要点分段。与同小节问题矛盾的“无问题”候选删除。
- **合成**：从已确认样本派生，报告段落和事实卡不变，只改条文；`base_sample` 记录来源样本。
  - 条文改写（`clause_override`）：答案随条文变化，由模型撰写，并设 `must_quote`；
  - 条文全不适用（`mapped_override`）：换成无关条文，意见不变，`clause_ids` 为空，依据为评审经验。
  - 合成样本合计不超过训练集的 30%，按 `splits.yaml` 的 `synthetic_cap` 检查。
- 规则专项样本见第十节。

## 十、专家规则预制（方案 v4 2.12）

**目的**：把指定的专家规则训练进模型。上线时，输入中只放一行规则标签即可开启这项审核，不附规则全文。规则库是离线资产，只在造样本和训练时使用。

### 1. 规则在样本中的三个位置

| 位置 | 字段／写法 | 用在哪类样本 | 作用 |
| --- | --- | --- | --- |
| 规格中的规则编号 | 样本和要点的 `rules`，例如 `['R-BASIC-CONTENT']` | 领域样本 | 记录该要点对应哪条规则，用于按规则统计和均衡；编号必须在 `rules/rules.yaml` 中 |
| 输出中的规则编号 | findings 的 `rule_id`，取要点 `rules` 的第一个；规则专项输出的 `rule_id` | 领域样本、规则专项 | 模型学会给每条意见标出所依据的规则，评测时可按规则和 L1–L4 分层统计 |
| **输入中的审核重点** | 一行【审核重点】，每项写成“规则标签（规则编号）”，标签取 `rules.yaml` 的 `tag` | **全部样本**：领域样本和规则专项 | 告诉模型本小节要检查哪些方面；输出的 `rule_id` 取自其中。规则专项训练时只带标签、不带规则卡全文，即上下文蒸馏 |

推理过程中写规则的判断步骤时：

- 领域样本标注“依据：评审经验”；
- 规则专项样本标注“依据：评审经验（规则 L3-07）”。

规则的判断步骤和阈值可以来自规则卡，不要求出现在输入中，其余事实仍须来自输入。

### 1a. 领域样本的审核重点

- **按章节类型自动带**：对应表为 `data/specs/focus_map.yaml`，写法与条文对应表相同。
  - 按 ptype 分三套：经常性、新建工程、政策；
  - 小节按 kind 取，摘要小节 `abs_xxx` 沿用正文小节；比对包按 `pack:` 条目取；
  - 训练和上线用同一张表。
- **审核重点不等于一定有问题。** 表里的规则是本小节应检查的方面，专家可能只对其中一两项提了意见。模型由此学会逐项检查、只对有问题的方面出具意见，不会为了对上标签而硬找问题。
- **不按专家意见实际涉及的规则来填。** 那样训练时“标签里有 = 一定有问题”，上线时误报会升高。
- **反向要求**：要点用到的规则必须都在对应表中，构建时核验。新项目出现表里没有的规则时，先判断该规则是否本就应在这类章节中检查，是则补进对应表，不为单条样本加例外。
- **示例**：经常性项目的成本核算小节为：

  “【审核重点】成本打开至末端（R-COST-OPEN）；成本归集口径（R-COST-ATTRIB）；对标对象可比性（R-COST-BENCH）；数量核定依据（R-COST-QTY）；单价核定依据（R-COST-PRICE）；成本周期性（R-COST-CYCLE）；成本数据一致性（R-COST-CHECK）；标准现行有效（R-STD-CURRENT）；问题建议针对性（R-SUGGEST-QUALITY）”

- **系统提示**中写明：逐项检查，只对发现问题的方面出具意见，rule_id 取审核重点中括注的规则编号。
- **预制规则加入对应表的时机**：规则卡经专家确认、专项样本进入训练后，再把该规则加入相应章节，例如 L3-07 加入 perf。在此之前，普通样本不带该规则，避免它在普通样本里大量出现却从不触发意见，与专项训练相互抵消。加入时按第 6a 小节补普通样本的意见。

### 1b. 规则专项样本的审核重点

- 只带本规则一项，例如“【审核重点】指标与成本关联（L3-07）”，位置在【任务】之前，与领域样本相同。
- 规则卡的 `tag` 必须与 `rules.yaml` 一致，不一致时构建报错。

### 2. 规则库与规则卡

- **规则库** `rules/rules.yaml`，现有 31 条。
  - 每条的字段：rule_id、tag（规则标签，进入【审核重点】）、level、question、judgment_points、policy_anchor（条文编号）、origin、source_cases、industries、valid_period、status；需要专项预制的规则另有 rule_card。
  - level 的含义：L1 红线、L2 结构、L3 逻辑一致、L4 专家判断。
- **规则卡** `rules/cards/<规则>.yaml`，由业务专家确认。字段如下：
  - `tag`：规则标签，须与 `rules.yaml` 中的 tag 一致；
  - `caliber`：判定口径；
  - `scope`：适用与不适用的范围，以及待专家定口径的问题；
  - `steps`：判断步骤；
  - `output`：判断结果的取值和输出字段；
  - `policy_anchor`：政策依据，须核对原文；
  - `examples`：5–10 个正反例；
  - `risk`：主要误判风险。

### 3. 五个步骤

| 步骤 | 做法 | 本项目的落实 |
| --- | --- | --- |
| 1. 规则卡 | 写判定口径、适用范围、判断步骤、正反例 | `rules/cards/L3-07.yaml`，草稿，待专家确认 |
| 2. 拆成子任务 | 把模糊判断拆成逐项判断 | L3-07 拆成两个子任务，见下方说明 |
| 3. 专项样本 | 老师带规则卡生成判断，经脚本核验和专家抽查；包含正例、反例、“合规但不适用”，以及同一内容改写成对的样本 | 规格写在 `rules/L3-07/<P>.py` |
| 4. 上下文蒸馏 | 训练输入只带【审核重点】一行，训练目标是第 3 步带规则卡生成并核验过的判断 | `out_rules/L3-07/train_tag.jsonl` |
| 5. 内化验证 | 同一批题目跑三组：带规则卡、只带标签、都不带。只带标签的效果接近带规则卡的，说明内化成功 | `eval_card`、`eval_tag`、`eval_none.jsonl` |

L3-07 的两个子任务：

1. **逐项判断**：对每个指标判断驱动成本、无对应成本项、需人工核对或不适用；
2. **汇总**：主要成本项是否都有指标覆盖，列出无对应成本项和需人工核对的关键指标。

L3-07 的判断口径、关联机制要求和量化方法，统一见**第十三节“定性指标与时效指标的处理”**。

### 4. 专项样本规格 `rules/<规则>/<P>.py`

- `SOURCE`：项目编号。
- `TABLES`：指标表 `ind` 和成本构成表 `cost` 的位置，PDF 为页加锚点，docx 为行号。
- `ITEMS`：逐项判断。每项包括 indicator、category、judgment、cost_items、direction、evidence、reason、think。
- `SUMMARY`：汇总。包括 covered、uncovered、unlinked、suggestion、think。
- `SYNTHETIC`：改写成对的样本。`replace` 用于改写指标表的一行，`item` 为改写后的判断。

逐项判断的输入依次为：规则卡、规则标签或两者都不带，然后是绩效指标表、成本构成表、待判断指标和任务。汇总的输入把待判断指标换成逐项判断结果。

规则专项的输出：

- 逐项判断：`{task:'规则专项', rule_id, step:'逐项判断', indicator, category, judgment, cost_items, direction, evidence:[{quote}], reason}`；
- 汇总：`{task:'规则专项', rule_id, step:'汇总', covered, uncovered_cost_items, unlinked_key_indicators, suggestion}`。

### 5. 核验（`scripts/build_rule_samples.py`）

1. judgment 只能取规则卡规定的值。
2. 证据摘录和 think 中的「引文」逐字出现在输入中。
3. think 中的算式逐个复算。
4. 判为驱动成本的，必须列出成本项。
5. 汇总中的 unlinked、manual 必须分别与逐项判断中“无对应成本项”“需人工核对”的指标完全一致。
6. 带规则卡的输入中，正反例要排除当前项目的例子，避免把答案放进输入。

### 6. 进入训练的条件

- 规则卡经专家确认之前，`splits.yaml` 中设 `in_train: false`。此时专项样本状态为“候选-规则卡待专家确认”，不进训练文件。
- 专家确认之后，按以下顺序操作：
  1. 按确认的口径修改 `rules/<规则>/<P>.py` 中受影响的逐项判断，重跑核验；
  2. 设 `in_train: true`、`train_variant: tag`，由 `make_splits.py` 生成 `rule_<规则>_train_think.json`、`rule_<规则>_train_nothink.json`，并登记进 `dataset_info.json`；
  3. 把该规则加入 `focus_map.yaml` 相应章节的审核重点，并按第 6a 小节补普通样本；
  4. 训练时与普通样本一起列入 LLaMA-Factory 的 `dataset`，例如 `audit_train_think,rule_L3-07_train_think`，一次训练完成。
- 开发集、测试集项目自动生成内化验证三组。
- 测试集必须包含“合规但不挂钩”的指标，例如效益、满意度类，并单独统计这一类的误报率。
- **比例控制**：只作用于训练集，开发集和测试集的内化验证题全部保留。
  - 每个项目的“不适用”逐项判断最多取 `keep_na_per_project` 条（现为 2 条）。这类判断简单，重复多了价值不大，但需要保留几条防止误报。
  - 专项样本行数 = 普通样本行数 × `rule_ratio`（现为 0.5，即普通 : 专项 = 2 : 1）。`make_splits.py` 按 6 类（汇总、合成、驱动成本、不适用、无对应成本项、需人工核对）平均挑选，类内各项目轮流取，保证各项目、各类判断均衡。
  - 每条规则的取数写在 `split_report.txt` 中；`in_train=false` 时也报告打开后的预计取数。
  - 有了开发集后，按效果调整这两个参数。
  - 现状（2026-10-23）：训练项目专项样本 1031 条，其中汇总 111、合成 57、驱动成本 464、不适用 168、无对应成本项 137、需人工核对 94；按 2 : 1 取 360 条（普通 721 条），各类 57–61 条，涉及 109 个项目。
- 改写成对的样本计入合成上限。
- 数据量：每个项目的专项样本按第 7 小节控制在约 8–15 条（驱动成本、无对应成本项、需人工核对各条，加汇总 1 条、改写成对 1 条，不适用最多 2 条）。另请专家精标约 20 个项目的指标，用于定口径和作测试集。
- **已生成的专项样本不删除**：2026-10-16 之前生成的专项样本（P001–P008、P011、P013、P090 等）按旧规则写了全部指标，数量偏多，保留原样，只在训练时由 `make_splits.py` 按上限取舍。取舍规则不变：优先汇总、合成、无对应成本项和需人工核对，每个项目至少保留 1 条不适用。
- **专项样本占比**：2026-10-23 用户定为普通 : 专项 = 2 : 1，按分类平均挑选（`rule_ratio`）；有了开发集后如需调整，由用户决定。

### 6a. 与普通样本的衔接

把规则加入普通样本的审核重点时，不能只加标签、不加意见。专家在普通小节里很少提这条规则；只加标签，模型会学成“这一项一般没问题”，与专项训练相互抵消。做法如下：

1. **范围**：取审核重点含该规则的普通小节，例如 L3-07 对应绩效基线类小节（perf），且小节内含指标表。
2. **补意见**：用该项目专项样本的汇总结论（SUMMARY）补一个要点。
   - `text_source='模型撰写'`，`source_kind='model_supplement'`，`reason` 写“规则预制：取自 <规则> 专项汇总”；
   - `rules` 为该规则；
   - problem 写无对应成本项、需人工核对的关键指标和未覆盖的主要成本项，suggestion 取汇总的 suggestion；
   - 按第七节公文风撰写，受写作规范检查。
3. **推理**：think 中增加一段规则判断，引用指标表和成本表原文，标注“依据：评审经验（规则 <编号>）”。原有的专家要点和推理保持不变。
4. **结论一致**：普通样本补的意见必须与专项汇总的结论一致。汇总中与该绩效小节指标有关的每一项结论（无对应成本项、管理要求类、需人工核对、缺数量指标、主要成本项未覆盖），都要在普通样本中有对应意见，依据不在小节中的先补事实卡。专项判断或口径改了，普通样本同步补改，新增的要点列入下一轮专家确认。
4a. **专家已提过的不重复补**：同一小节的专家原话已指出相同问题时，不新增模型撰写的要点，只在该专家要点的 `rules` 中加上该规则，意见仍用专家原话。例如 P002 专家指出“考生出考率”应改为报名缴费考生数，与 L3-07 汇总一致。专家只说到一部分的，只补专家未提的部分。
5. **不触发的情况**：汇总结论为“指标与成本挂钩良好”的项目，不补意见。审核重点照样带该规则，模型由此学会“检查过、没问题就不写”。
6. **不送专家确认**：L3-07 衔接要点（规则预制）按沪财绩〔2024〕15号、〔2025〕8号和《指标到成本计算规则》由我方判断，不列入专家确认表（用户 2026-10-19）；reason 写“规则预制：取自 L3-07 专项汇总（标准第十节 6a）；已按沪财绩〔2024〕15号、〔2025〕8号判断”。以后同类规则判断照此处理。其他模型撰写的要点（模型补充发现）已全部采纳，不再送专家确认。

### 7. 每个新项目同步生成专项样本

**规则**：每个新项目做完普通样本（`data/specs/<P>.py`）后，同步为当前的每条预制规则生成专项样本，不等到规则卡确认后再补。当前的预制规则只有 **L3-07**。

步骤：

1. **定位表格**：在报告中找绩效指标表和成本构成表，写入 `TABLES`。各类项目的取法：
   - 经常性项目：取关键绩效指标表和历史成本梳理表（或支出明细表）；
   - 新建工程：取绩效指标表和支出标准建议表（投资估算结构）；
   - 政策项目：取绩效目标表和政策支持方向及内容表（扶持标准）。
2. **逐项判断**（2026-10-16 起，控制生成量）：`ITEMS` 只写以下四类，**其余指标不写**：
   - 判为**驱动成本**的；
   - 判为**无对应成本项**的；
   - 判为**需人工核对**的；
   - **不适用**的最多写 **2 条**，优先选效益类和成本指标各 1 条（让模型见到“不判为问题”的样子，防误报）。

   判断时仍须逐个看过指标表中的全部指标，没写进 `ITEMS` 的指标视为不适用。汇总的 think 中，对没写进 `ITEMS` 的不适用指标，只写“其余效益、满意度和成本类指标不适用”，不写具体个数（个数无法在输入的逐项判断结果中核对）。

   判为驱动成本的，reason 和 think 必须写出关联机制（见第十三节第 3 小节），时效类对应值守人员和设备配置，成本表未列的注明“成本构成表未列”；判为需人工核对的，按第十三节第 4 小节给出适合该指标的量化方向，不写具体数值。判断按规则卡的步骤进行；遇到规则卡未覆盖的口径，按最接近的口径判断，在 reason 中注明“待专家确认”，并把该问题补进规则卡的 `open_questions`。
   **写法**：不要为每个项目另写生成脚本。复制 `rules/L3-07/_模板.py` 为 `P<编号>.py`，用 `rules/L3-07/lib.py` 的 `drv`、`mgmt`、`manual`、`na` 四个函数写 `ITEMS`（证据行由函数从原文取，保证逐字），项目文件里只写“判断了什么”。
3. **汇总**：写 `SUMMARY`，`unlinked` 必须与逐项判断一致。
4. **改写成对**：每个项目至少一组 `SYNTHETIC`，把一个指标改写为能明确对应成本项的指标，优先改写无对应成本项或需人工核对的指标（如把“及时”改为明确时限）。改写内容不得引入报告中没有的数字。
5. **核验**：运行 `python3 -I scripts/build_rule_samples.py data L3-07`，rejected 为 0。
6. 规则卡确认前，这些样本不进训练文件（`in_train: false`）。

## 十二、容易犯的错误（均已发生过，构建时会拦截或需自查）

1. **改写专家原话。** 依据可达的要点一律用原话。觉得原话啰嗦、不够公文，也不改。
2. **对专家原话套用写作规范。** 写作规范只约束模型撰写的意见。
3. **意见中写条文编号**，或在意见结尾的括号里列条文。条文只在 think 中引用。
4. **数字不在输入中。** 例如把 811.75 写成 811.76，或沿用专家的取整数字“800万”。专家原话中的数字也须核验：取整的按最小改动换成精确值并登记；笔误按已确认的值修改。
5. **依据不可达却按可达处理。** 依据在其他小节时，先补事实卡；补不了就按第四节 A/B/C 三类处理，不能直接用专家结论。
6. **口语化**，例如本小节、请到、看不到、我们。
7. **矫枉过正。** 例如“仅”“未”用得过多，分句过长。按第七节的量化要求写。
8. **证据摘录不逐字**，或锚点切错范围。以构建报错为准，修正锚点后重跑。
9. **状态和来源写错。** 自动标注项目不得写“专家已采纳”。`status` 只写真实的确认进度。
10. **使用旧方法的残留。** 规格之外不再有覆盖层，不再有 revise、merge、structured、expert_verbatim 等文件。修改样本只改 `data/specs/<P>.py`，然后重跑构建。
11. **随意简化推理过程。** 修改 think 时保持原有的核对步骤和长度。
12. **按专家意见实际涉及的规则填审核重点。** 审核重点一律按章节类型从 `focus_map.yaml` 取，不按答案反推。
13. **新项目只做普通样本、漏做专项样本。** 每个新项目都要同步生成当前预制规则的专项样本（第十节第 7 小节）。
14. **把所属部分写进意见正文。** 部分名只作标签，正文从问题或建议直接写起。
15. **事实表述过头**：金额归属扩大、把部分说成整体、把近似说成绝对、把口径不同说成不一致。见第七节“事实表述的准确性”。
16. **硬性建立关联**：为了让每个成本项都“有指标覆盖”，把不相干的指标和成本项、问题和建议连起来。见第十三节第 3 小节。
17. **定性指标处理不一致**：只写“及时”的直接判驱动成本、量化方向套用不合适的方式、写出模型自拟的具体时限，或者专项汇总与普通样本意见对同一指标说法不一。见第十三节。

## 十三、定性指标与时效指标的处理（所有样本通用，动笔前必读）

**上位依据：`data/rules/指标到成本计算规则.md`**（据沪财绩〔2024〕15号、沪财绩〔2025〕8号整理）。判断指标与成本的关系时，先按该文件确定指标在成本公式中对应的因子（数量因子、配比因子、频次因子、单价），再按本节写作。两者不一致时，以规则文件的政策依据为准，并报专家确认。

本节集中写明指标类问题的判断口径、关联机制、量化方法和写法，不论在样本的哪个部分写指标，都按本节执行，包括：
- 普通样本的推理过程和模型撰写的意见（补充发现、L3-07 衔接意见）；
- 专项样本的逐项判断、理由和汇总；
- 批量标注新项目时生成的上述内容。

本节内容来自专家第六轮确认的口径、第七轮的修改意见，以及历史报告和公开资料，2026-10-16 按 15 号、8 号文统一。以后有新的口径，在本节和规则文件第五节同时记录；专家口径与政策原文不一致时，按政策执行并告知专家。

### 1. 什么是定性指标

标杆值没有量化，只写定性表述的指标，例如：
- “及时”“有效提升”“显著”“健全”“整洁完好”“准确”；
- 只写“参考某导则”，未说明具体要求；
- 比率类指标未说明计算口径和标准，例如及时率未写明时限。

### 2. 判断口径（专家第六轮确认，2026-10-16 按 15 号、8 号文统一；规则卡 `rules/cards/L3-07.yaml` 的 decision，统一记录见规则文件第五节）

| 指标类型 | 例子 | 判断 | 成本关联机制（必须写出） |
| --- | --- | --- | --- |
| 时效类，**只写“及时”**（服务、作业、工程本身的完成或响应时效，含“及时率”“及时性”，按计时对象划分，2026-10-19） | 考试组织工作完成及时性、应急处置及时性、杂志出版及时率、项目开竣工及时性 | **需人工核对**（无量化表述） | 暂不建立关联；给出量化方向（第 4 小节）。审核、报告和资料提交、检查、验收、考核、结项等管理动作的“及时”，按下方常规性管理要求判断 |
| 时效类，**有明确时限** | 抢修 2 小时内到场、建设工期 6 个月 | 驱动成本 | 时限 → 值守人员、班次、车辆设备配置 → 人工和设备成本、夜间节假日出勤附加费；工期 → 监理等按时间计费的服务 |

| **合格率、达标率、完好率、畅通率**（质量指标） | 养护考核合格率、考务人员资质达标率、场地设施设备完好率 | 驱动成本（配比因子或单价因子） | 写出达标所需的配置（人员、设备、频次）或须执行的标准 |
| **验收合格率**（按被验收对象划分，2026-10-19） | 工程一次验收合格率、设施设备验收合格率、印刷品验收合格率 | 驱动成本（配比因子或单价因子） | 写出验收标准或达标所需配置对应的成本项，例如建安工程费单价、监理检测费；考核、检查、评审得分“通过”类和报告、课题等文档成果的验收通过率仍按常规性管理要求判断 |
| 质量要求的定性表述 | 绿化养护质量“整洁完好” | 驱动成本（质量越高投入越高） | 质量要求 → 作业频次或单价 |
| 执行某标准 | 出水执行 GB16889、种植参考绿化导则 | 驱动成本 | 标准 → 工艺、苗木规格 → 单价 |
| 报告列为效益、实质是过程质量要求的 | 环保施工达标率（施工环保措施符合规范的比例） | 驱动成本（按质量指标判断） | 写出达标所需的措施配置 |
| 效益类、满意度类 | 社会知晓率、公众满意度、恢复生态系统功能 | 不适用（不判为问题） | 效益指标通过决定产出间接影响成本，不直接进入成本公式；可指出与之对应的产出指标 |
| 成本指标本身 | 投资控制“按批准概算控制” | 不适用 | 它本身是成本约束，不是成本动因 |
| **常规性项目管理要求类**（考核、检查“通过”类和“及时”类结果指标，先按此类判断） | 季度考核完成率、维护监管工作考核通过、项目审核及时率、政策扶持资金发放完成率、补助发放准确性 | **无对应成本项** | 注明“属于常规性管理要求类指标”，建议替换为作业数量类指标；依据：15 号文“不应设置如常规性的项目管理要求等与产出、效益和成本明显无关联的指标” |
| 其他不改变任何资源投入的 | 考生出考率 | 无对应成本项 | 写明为什么不改变投入，以及与成本直接相关的应是什么（如报名缴费考生数） |
| 政策项目只计个数的数量指标 | 建设引领型项目“1个及以上” | 驱动成本 | 汇总中指出：扶持资金按投资额比例计算，个数难以反映资金规模 |

### 3. 关联机制必须符合常识（第七轮）

1. **三段式机制**：判断驱动成本时，必须写出“指标值变化 → 哪种资源投入（人员、班次、车辆、材料、频次、单价）随之变化 → 落到哪个成本项”。说不清的，不建立关联。
2. **不凑成本项**：成本构成表中没有对应费用的，写“××（成本构成表未列）”，并列入汇总的未覆盖项，不拿相邻的成本项凑数。
3. **时效不等于工作量**：及时率、响应时限反映响应速度，对应的是值守配置，与工程量无关，不能从及时率推出要补充工程量指标。
4. **不可计划的工作量**（抢修、故障维修）用抢修率、故障率乘以设施总量表示，例如 P001 报告的标志板抢修率≤8%、杆件抢修率≤5%；写“未设置”之前，先查报告有没有这类基线。
5. **按费率计取的费用不随工期变化**：建设单位管理费一般按投资额的费率计取，不与工期挂钩。

**已发生的反例**（均已改正）：

| 原写法 | 问题 | 改为 |
| --- | --- | --- |
| P001：抢修相关指标仅为及时率，建议补充标志板、杆件、标线等抢修工程量指标 | 及时率与工程量无关；报告表3-7 已有抢修率基线 | 删除该意见；专项判断改为对应“应急值守和出勤费用” |

| P004：建设工期对应建设单位管理费和工程监理费 | 建设单位管理费按费率计取，不随工期变化 | 只对应工程监理费，并写明不作关联的原因 |

### 4. 定性指标的量化方法

判为需人工核对，或在意见中指出“缺少量化”时，按指标的性质从下表选择量化方向。

| 方式 | 写法示例 | 适用 | 来源 |
| --- | --- | --- | --- |
| 响应时限 | 接报后若干分钟内响应 | 运维、报修 | 历史报告（运维 15 分钟、维修 20 分钟内响应） |
| 到场时限（可按区域、等级分档） | 紧急抢修若干小时内到场 | 抢修、应急处置 | P001 报告；GB/T 48259—2026 井盖运维“接报后 2 小时内到达现场” |
| 完成或修复时限 | 一般维修若干小时内完成 | 维修、缺陷处置 | P001 报告；道路照明报告“危急缺陷不超过24小时” |
| 按时完成率 | 按时完成数 ÷ 总数 × 100%，**必须同时写明时限标准** | 有时限要求的任务 | P001 报告；地方绩效目标表“故障设备维修及时率 100%”配“故障响应时间≤1440 分钟” |
| 频次或周期 | 把“推送及时率”改为“半月一次”推送频次；按维护内容明确清理、检查周期 | 日常性、周期性工作 | 外经处、社保处专家意见 |
| 时间节点 | 按考试计划明确关键环节完成时点；考后若干个工作日内公布成绩；开工、竣工时限 | 有计划节点的工作 | 教科文处专家意见 |
| 时长 | 展览搭建时长（天）、撤展时长（天） | 一次性活动 | 社保处专家意见 |
| 可衡量的效益指标 | 有责环境污染事故发生数、主要污染物削减率、参观接待批次 | 定性的效益指标 | 经建处专家意见（老港项目） |

依据：财政部《中央部门项目支出核心绩效目标和指标设置及取值指引（试行）》。时效指标反映完成的及时程度；有时限要求、关键时间节点明确的，分解设置约束性时效指标；内容复杂的，按工作周期或频次设定。

### 5. 写法要求

- **不写具体数值**：量化方向写“若干小时内”“若干个工作日内”，具体时限取合同约定、行业标准或历史实际，不由模型自拟。
- **推理过程**按以下格式写：

  - 时效类：“步骤1（类别）→ 步骤2（量化：标杆值是否有时限）→ 步骤2（找成本项：时限对应哪种投入）→ 结论”；
  - 需人工核对：写明“未规定具体时限，无法据此判断对应哪种资源投入”，再给出量化方向和量化后对应的投入。

- **意见措辞**：
  - 写“标杆值为‘及时’，缺少量化时限，建议明确……时限”；
  - 不写“反映不了”“没有任何”等绝对化说法（见第七节）。
- **专项与普通样本一致**：同一项目的专项汇总和普通样本的 L3-07 意见，对同一指标的判断和量化方向必须一致。

### 6. 自查清单（每写一条指标判断或指标类意见都过一遍）

1. 这个指标的标杆值是定性的吗？是的话，按第 2 小节归类。
2. 判为驱动成本的：能否写出“指标变化 → 资源投入变化 → 成本项”三段？成本项在成本构成表里真的有吗？
3. 是否从时效指标推出了工作量，或把两个不相干的事项连在一起？
4. 写“未设置”“未涉及”之前，查过报告其他部分是否已有相关基线或指标吗？
5. 需人工核对的，量化方向是否适合这个指标的性质（应急→到场时限，日常→周期，考试→时间节点）？
6. 有没有写具体数值？有的话，该数值是否出自输入或推理中的验算？
18. **口径冲突未处理**：专家口径与政策原文不一致时，没有记录就照用其中一方。先在规则文件第五节记录，再按政策执行并告知专家。
19. **把专家当作意见来源。** 推理和模型撰写的意见里写“专家所指／所称／指定／要点……”（2026-10-22 起由 `SRC_EXPERT` 拦截，2026-10-23 扩充了所称、所说、指定、要点等词）。
20. **专家与报告对不上的意见写成提示核实。** 专家数字与报告不符、专家意见与现有报告不符的，不生成样本，记入 `data/out/unlinked_expert_comments.json`（C 类，2026-10-23）。
21. **漏补 L3-07 衔接。** 专项汇总中“无对应成本项”“需人工核对”的指标结论，普通样本的绩效小节必须有对应的模型撰写要点（第十节 6a 第 2、4 条）；只有专家已提同一问题时才只加规则标签。2026-10-23 审查发现第 16–20 批共 13 个项目漏补，已补。
22. **把效益、可持续影响、满意度类指标判成“无对应成本项”。** 这类指标按第十三节第 2 小节判“不适用”；“无对应成本项”只留给考核、检查、验收通过类和准确性类的常规性管理要求指标。2026-10-23 审查发现 P032、P033、P037、P047、P054 误判，P035 改选，已改。
23. **报告原文里数字间的多余空格未清理。** 如“3 ,783.78”“66. 19%”“100.00 %”，会被样本照抄；转换后统一并入（`data/raw/reports/<P>.md`）。
24. **提示核实样本中答案和推理引入输入里没有的事实。** 旧的提示核实由模型另写“应核对哪一章的什么内容”，答案里的表号、页码、附件名、“全文未出现”在输入中都没有，推理也只能照着专家意见倒推。2026-10-23 起整类移除：报告缺内容的改成正常样本（A），依据在报告之外的和与报告不符的单独存放（B、C）。检查时注意：问题表述必须能从输入读出；“全文没有”这类断言，输入只是小节时不能写，只能写“本小节没有”。
25. **推理引用输入里没有的表号、附件号、页码。** 推理里写“表3-2”“附件3”“第N页”，而小节摘取时表题行没有取进来，模型无从知道是哪张表。2026-10-23 审查发现 180 个样本如此：表题行在小节旁几行内的，把表题行补进该小节的行区间（spec 里 `SECTIONS[...]['lines']`）；表题距离较远、小节也不含该表的，推理改称“相关表格”；专家原话里自带的页码、文件名属于原话，不改。`build.py` 的 `ENT_REF` 检查：推理里的表号、附件号、页码必须出现在输入或意见里，否则拒绝。

## 十四、仿写样本（2026-10-26 起；用户同意，用于补薄弱规则）

**为什么有这一类**：没有新项目资料，而部分规则的真实样本太少（训练意见不足 15 条），或开发集上长期命中为 0。允许在现有真实报告上“仿写”：输入是真实小节，意见和思考由标注者按专家口吻撰写。它**不是专家意见**，在样本里标 `source_kind: imitation`，计入合成样本，与其他合成样本合计不得超过训练集的 30%（`make_splits.py` 的 `SYN_KINDS` 已含 `imitation`）。

**两种来源**
1. **真实缺陷**：输入取自 `data/cand/cand_inputs.jsonl`（专家没有提过意见的真实小节，由 `scripts/build_candidate_inputs.py` 生成）；标注者读完小节，只在发现**具体、可核验**的问题时写意见。
2. **人造错**：对真实小节做最小改动（登记在 `edits` 里，旧值必须在小节正文中恰好出现一次），例如把文字里的合计改成与表不一致、把合计行改小；原文本身勾稽一致，改动后的差异是确定的。写在 `meta.edits` 里。

**写法要求**（与第七节一致，并增加以下几条）
- 意见必须具体：带数字、引文或输入小节中的具体词语，不得写成“补充 XX”“加强合理性分析”“完善依据”这类泛泛要求（`build_imit.py` 会拦截）。
- 数字和算式写在思考里并可复算；意见里的数字须在输入中或在思考里验算过。
- 不确定的写“未说明”“需核实”，不下“有错”的断言；不把推测写成事实。
- 薄弱规则以外的规则只在小节里确有具体问题时才写；不为凑数量而写。
- 规则必须在该小节【审核重点】里；条文编号必须在输入的条文中并在思考里引用。
- `reason` 写仿写依据：对应哪条规则的哪个判断要点；人造错写明改了什么。

**构建**：`python3 -I scripts/build_imit.py data data/imit/<批次>.py ...`，输出 `data/out_imit/`（samples.jsonl、rejected.jsonl、preview.md）。被拒绝数必须为 0。每批 20 个样本，抽查后再继续。

**用途与限制**
- 用于 T0 增量：训练集 = `data/out/samples.jsonl` + `data/out_imit/samples.jsonl`（`splits` 里另配 `samples_file`）；开发集和测试集**不使用**仿写样本。
- 不进入 BASIC-CONTENT、BASIC-BUDGET、COST-QTY 三条规则：这三条训练意见已多，但开发集上额外意见大多不成立（2026-10-26 人工判定），再加正例会加重泛泛输出。
- 政策类规则（R-POL-*）暂不仿写：真实的未标注小节几乎没有。
